# Unity 2D 开发规范与防死循环技能

此技能是 Unity 2D 项目的强制开发指南。**在编写或修改任何 .cs 脚本之前，必须先阅读并遵守本技能中的所有规则。**

---

## 一、核心铁律（最高优先级）

### 1.1 编译通过即合格
> **只要代码可以在 Unity 中正常编译、游戏可以正常运行，就判定为可用。**

- ❌ 不要因为"代码不够优雅"而反复修改已能正常工作的脚本
- ❌ 不要主动追求极致整洁、过度重构、持续微调
- ❌ 不要因为命名风格、注释格式、代码排版等非功能性问题发起修改
- ✅ 只有当 Unity 报编译错误、运行时崩溃、空引用异常、逻辑死循环时才需要修复

### 1.2 非致命问题不修改
以下情况**不属于必须修复的范围**，除非用户明确要求：
- 大括号数量通过 grep 统计不匹配（注释和字符串内的 `{}` 会导致误报）
- 代码格式/缩进不统一
- 变量命名不够语义化
- 可以优化但当前能正常工作的逻辑
- 缺少某些"最佳实践"但不影响游戏运行

## 二、防死循环与迭代限制

### 2.1 硬性迭代上限
- **同一个问题最多尝试修复 1 次。** 一次修复完成后立刻停止，禁止反复读取文件持续微调。
- **如果连续 2 次调用工具用于修复同一个非致命问题，立刻停止迭代**，向用户汇报现状，禁止自主无限循环调整代码。

### 2.2 禁止重复调用
- **禁止无意义重复调用相同 bash 命令** — 相同 bash 指令在没有用户新指令的情况下不得重复执行。
- **禁止主动执行 bash 命令统计大括号 `{}` 数量** — 此方法存在大量误报，不作为代码校验手段。
- **禁止循环遍历所有 .cs 文件做语法检查** — 仅在用户明确要求时才执行。

### 2.3 读取上限
- 单次任务文件读取上限：**最多读取 3 个 .cs 文件**。
- 当连续读取文件超过 **15 秒** 没有进展时，主动放弃检索，向用户汇报现状。

### 2.4 自我检测
在发起任何工具调用前，先在心里问自己：
1. 这个操作我刚才是不是已经做过了？（是 → 停止，换个思路）
2. 这个文件我刚才是不是已经读过了？（是 → 不要再读）
3. 这个修改是否真的有必要？（没有编译错误/运行正常 → 不改）

## 三、文件编辑纪律

### 3.1 编辑前必做
1. **先读取文件** — 确认当前文件内容后再修改，不要凭记忆或猜测
2. **想清楚再改** — 明确知道改什么、为什么改、改完后的预期效果
3. **一次改到位** — 同一处逻辑问题在一个 Edit 调用中完成，不要改完又发现漏了什么再改

### 3.2 禁止"添加-删除-再添加"循环
这是最容易陷入的坏习惯：
- **一旦添加了代码，就不要在同一个对话轮次中立即删除它** — 除非编译器报错证明它有问题
- **不要对同一段代码反复"调整"** — 改完一次就停下来评估，不要接着改第二次
- 如果发现自己刚添加的代码又想删掉 → **先停下来思考**，等确认清楚再操作，不要凭冲动行事

### 3.3 文件写入失败处理
当文件编辑操作反复失败时：
1. **立刻停止尝试修改该文件**，不进行重试、不反复生成补丁
2. **输出完整新代码文本**，让用户手动复制覆盖文件
3. 不要持续发起文件写入/补丁修改请求，避免无限循环卡死
4. **禁止反复自动修改核心游戏脚本**（如 CameraZoneManager.cs、player.cs 等）

---

## 四、思考与阻塞控制

### 4.1 不要无限阻塞思考
- 当连续思考或读取文件超过合理时间没有进展，**主动终止当前思路**
- 向用户汇报：你卡在哪里、需要什么信息、建议下一步怎么做
- **宁可不做也不要卡死** — 用户可以通过新指令重新引导你

### 4.2 决策速度优先
- 如果某个问题有两种差不多合理的方案，**选一个先做**，不要长时间对比分析
- 技术选型的决策时间 ≤ 30 秒思考（除非用户明确要求详细对比）
- 简单的代码修改直接动手，不要写长篇分析再去改

## 五、Unity 2D 编码规范速查

### 5.1 命名规范
- 类名：PascalCase（如 `PlayerController`）
- 私有字段：下划线 + 小驼峰 `_moveSpeed`
- Inspector 暴露参数使用 `[SerializeField]`，尽量少用 public 字段
- 但如果后期需要被其他脚本调用，毫不犹豫使用 `public`

### 5.2 2D 物理硬性规则
- **仅使用 2D 系列组件**：`Rigidbody2D`、`Collider2D`、`OnCollisionEnter2D`、`OnTriggerEnter2D` 等
- **不要生成 3D 物理相关代码**（Rigidbody、Collider、OnCollisionEnter 等）

### 5.3 空安全
- 访问任何 `GameObject`、组件前做空值判断
- 杜绝空引用报错

### 5.4 禁止行为
- 不生成 3D 物理相关代码
- 不滥用多线程直接操作 Unity 游戏对象
- 不使用第三方付费插件，优先原生实现
- 不主动重构需求之外的无关代码

### 5.5 API 命名规范（严禁臆造函数/属性名）
- **禁止凭记忆编造 Unity API 名称**。不确定时先查文档或搜索确认，而不是靠"猜"写代码。
- **2D 和 3D 的 API 命名差异很大**，常见混淆陷阱：
  - ❌ `Collision2D.attachedRigidbody` → ✅ `Collision2D.rigidbody`
  - ❌ `Collision2D.collider` → ✅ `Collision2D.otherCollider`
  - 3D 里才有的 API（如 `attachedRigidbody`、`GetContact(0).thisCollider`）在 2D 下不存在。
- **拿不准时原则**：写 2D 代码时，所有物理 API 必须先确认带 `2D` 后缀后的完整签名。从 `collision.gameObject.GetComponent<Rigidbody2D>()` 获取是最安全可靠的方式，不要投机取巧用不存在的属性。

### 5.6 平台/触发器检测：不要迷信碰撞回调的连续性

**这是本项目反复踩坑的核心教训。** `OnCollisionStay2D` 不可靠，不能用于持续状态跟踪。

**现象**：物理帧中如果出现短暂碰撞丢失、刚体休眠、微小浮空、浮点抖动，`OnCollisionStay2D` 会断帧不执行。在 FixedUpdate 中依赖碰撞回调设置的 bool 值做状态机会导致计时器无限重置、状态错乱。

**错误模式（禁止使用）**：
```
// ❌ 依赖 OnCollisionStay 每帧更新 _playerIsOn
void OnCollisionStay2D(...) { _playerIsOn = true; }
void OnCollisionExit2D(...)  { _playerIsOn = false; }
void FixedUpdate() {
    if (_playerIsOn) _timer += Time.fixedDeltaTime; // Stay断一帧，timer就乱
}
```
- **遍历 `contact.normal` 判断"站在上面"不可靠** — 边缘接触时多个 contact point 的法线方向不一致，`foreach` 遍历顺序不保证。

**正确方案优先级**：
1. **射线检测**（最推荐）— 从平台顶部向下多点采样 `Physics2D.Raycast`，不依赖碰撞回调，每帧主动探测。可以显示 `Debug.DrawRay` 辅助调试，`OnDrawGizmosSelected` 可视化。
2. **直接 `Rigidbody2D.position` 位移** — 移动平台同步玩家时，在 FixedUpdate 中直接改骑手 `Rigidbody2D.position`，不依赖父子层级（会被 velocity 覆盖）。
3. **碰撞回调只做事件通知** — `OnCollisionEnter2D` / `OnTriggerEnter2D` 用于触发一次性事件（如"碰到一次就启动倒计时"），不做持续状态跟踪。

**关键设计原则**：
- **理解需求语义后再选方案**。"踩上去一段时间后消失"在类银河恶魔城语境下通常是"触发即倒塌"（碰到一次立刻倒计时，不可撤销），不是"持续踩踏"（离开就取消）。写代码前先确认：是触发型还是持续型？
- **状态机尽量单向、不可逆**。不要随意添加回退路径——除非用户明确要求"离开后恢复"。你脑补的回退逻辑大概率是错的。
- **能用射线就不用碰撞回调做轮询**。射线是主动探测，碰撞回调是被动通知——轮询场景下前者远更可靠。

### 5.7 字典Key选择：能用引用就别用字符串

**今天踩的坑**：传送门管理器用 `doorId` 字符串做 `Dictionary` 的 key。用户拖入两个门时默认 doorId 都是 `"Door_01"`，同名冲突 → 第二个注册失败 → 从一个门进查到了错误的配对 → 传回自己。

**规则**：
- Inspector 中用户拖入的是**引用（GameObject/组件引用）**，不是字符串。如果你做 `Dictionary<string, XXX>`，就强迫用户必须手动填唯一 ID，增加出错概率。
- **优先用引用本身做 key**：`Dictionary<RoomDoor, RoomDoor>`。每个物体天然唯一，不需要用户多填任何东西。
- 只有明确需要跨场景/跨存档查找时（如存档系统），才用字符串 ID。

### 5.8 不要过度设计——用户没要求的功能别加

**今天踩的坑**：传送门加了 `direction` 枚举、`AutoWalkForward()` 自动前进——用户没有要求这些功能，事后被要求去掉。

**规则**：
- 用户说"传送后让玩家移动几步" → 先问清楚再实现，不要自己脑补方向枚举和自动走路协程
- 用户说"上下连接的房间" → 不要自作主张加 force walk 逻辑，他们的方案可能是给速度
- **每多加一个字段/枚举/模式，就多一个 Inspector 配置负担**。简单优先

## 六、输出规范

### 6.1 修改已有脚本
- 输出修改后的**完整代码**，标明改动区域
- 禁止只给出零散代码片段

### 6.2 注释规范
- 使用**中文注释**，不要使用英文注释
- 注释要详细，便于后期修改
- 对可在 Inspector 面板调整的参数，在注释中标注说明

### 6.3 代码风格
- 代码尽量简洁，避免冗余
- 遵循项目现有的代码风格，不要引入项目不使用的设计模式

## 七、执行检查清单（每次修改前过一遍）

在修改任何 Unity C# 脚本前，确认以下条目：

- [ ] 这个修改是否真的必要？（有编译错误/运行异常吗？）
- [ ] 我有没有读过要修改的文件？
- [ ] 这个操作我刚才是不是已经做过一次了？
- [ ] 我是不是在改一个"能正常工作"的代码？
- [ ] 如果文件写入失败，我是否准备好直接输出代码文本？
- [ ] 我确定这次修改不会在下一轮又被我自己删除掉吗？
- [ ] **我使用的每个 Unity API 名称都是真实存在的吗？（不凭记忆瞎编）**

## 八、应急退出

当出现以下任一情况时，**立即停止所有工具调用，输出总结并等待用户指令**：
1. 同一个文件连续 2 次写入失败
2. 同一个问题已经尝试修复过 1 次仍未解决
3. 发现自己正在进行"添加-删除-再添加"的循环
4. 连续 15 秒以上的思考/检索没有实际进展
5. 相同的 bash 命令即将被重复执行第 2 次
